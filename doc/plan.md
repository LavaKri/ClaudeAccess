# Plan — Interface web accessible JAWS pour `claude -p`

## Décisions d'architecture

- Projet Node.js avec `package.json`, Express (fichiers statiques + routes REST annexes) et le module `ws` pour le canal WebSocket (pas besoin de `socket.io` : pas de fallback polling ni de rooms nécessaires).
- Transport serveur ↔ navigateur : **WebSocket** (obligatoire dès qu'on veut le protocole de permissions interactif).
- Protocole de permissions : **interactif** dès la V1 (négociation en direct via le flux `stream-json`), plutôt qu'un simple `bypassPermissions`.
- Changement de répertoire de travail : via l'option `cwd` de `child_process.spawn`, pas de flag CLI dédié.
- Découpage : `server/` héberge toute la logique Node (spawn, WebSocket, sessions) ; `front/` est servi tel quel en statique par Express, sans build step ni bundler.
- `CLAUDE.md` et la documentation future : en anglais, pour permettre une éventuelle publication.

## 0. Initialisation

- `CLAUDE.md` en anglais (contexte projet, contraintes d'accessibilité JAWS, décisions d'architecture ci-dessus).
- Ossature `package.json` (Express, `ws`, `nodemon` en dev), `npm run start` / `npm run dev`, `git init` + `.gitignore`.

## 1. Mock du CLI

- Écrire le mock **en se basant sur la documentation** (`claude --help`) et sur les exemples déjà capturés (types `system`, `stream_event`, `assistant`, `user`/`tool_result`, `result`), sans bloquer sur une capture exhaustive du protocole de permissions.
- Le mock doit couvrir au minimum :
  - un scénario texte simple avec deltas progressifs et délai variable ;
  - un scénario avec appel d'outil (`tool_use` / `tool_result`) ;
  - un scénario de demande d'autorisation (permission interactive) mettant le flux en pause jusqu'à réponse ;
  - ~~un scénario `AskUserQuestion`~~ : abandonné, voir note ci-dessous (§4) — l'outil ne fait pas partie du protocole observable sur ce compte.
- Ces hypothèses seront confirmées/corrigées plus tard par une capture réelle ciblée (`--permission-mode manual` + `--input-format=stream-json`).
- Le serveur doit pouvoir invoquer indifféremment le vrai `claude` ou le mock (variable de config/env), pour basculer facilement pendant le développement.

## 2. Prototype minimal

- Formulaire → WebSocket → affichage progressif du texte (deltas), sans historique.
- Premier test JAWS ici : zone `aria-live="polite"`, pas de déplacement de focus intempestif pendant le streaming.
- Affichage minimal des `tool_use`/`tool_result` (au moins en texte brut), puisque le mock les inclut déjà.
- Bouton Annuler / tuer le process en cours, à côté du bouton d'envoi. Pendant que `claude` travaille : le champ prompt est en lecture seule, le bouton d'envoi est désactivé, et inversement seul le bouton Annuler est actif.
- Distinction prévue à l'origine pour l'étape suivante entre une **demande de permission** (question fermée : oui / non / oui-toujours…, champ prompt indisponible) et une hypothétique **`AskUserQuestion`** (question ouverte, champ prompt resté disponible en plus des suggestions) — devenue sans objet, voir §4 : `AskUserQuestion` a été abandonné, seule la demande de permission (fermée) reste implémentée.

## 3. Historique

- Historique en mémoire côté serveur (pas de persistance disque), effacé au redémarrage du serveur ou fermeture du navigateur.
- Bouton « Nouvelle session » (reset côté serveur + client).
- Gestion du titre de session (via `-n/--name` réel, ou stocké côté serveur pour le mock).

**Titre de session et suggestions de prompt (confirmés réels, plus des hypothèses) :**
- `--prompt-suggestions=true` déclenche bien un événement `{"type":"prompt_suggestion","suggestion":"...","session_id":"..."}` en fin de flux, après `result` — confirmé sur un vrai `claude -p` avec un prompt « actionnable » (un prompt trivial ne suffit pas à le déclencher). Champ : `suggestion` (pas `prompt`). Pas d'`id`/réponse attendue, fire-and-forget.
- Un titre de session est bien généré automatiquement pour toute session, y compris un simple `-p` (confirmé en inspectant directement `~/.claude/projects/<cwd-encodé>/<sessionId>.jsonl`, où apparaît une ligne `{"type":"ai-title","aiTitle":"...","sessionId":"..."}`). Il existe aussi `custom-title` (renommage manuel) et `last-prompt`. **Mais ça ne transite jamais par le flux `stdout`** — écrit de façon asynchrone dans le fichier de session sur disque. Le mock n'émule donc plus de faux événement de titre dans le flux ; le vrai titre sera géré à l'étape 3 (lecture du même fichier de session, comme le fait `claude-code-webui`).
- Encodage du chemin de projet vers le nom de dossier dans `~/.claude/projects/` (confirmé via le code de `claude-code-webui`) : `/`, `\`, `:`, `.`, `_` → `-`.

**Historique, sessions et répertoire de travail (fait) :** confirmé qu'aucun stockage propre n'est nécessaire — `claude` persiste déjà tout dans `~/.claude/projects/<cwd-encodé>/<sessionId>.jsonl`, et `~/.claude.json` liste déjà les répertoires de travail connus (`projects`). Le serveur (`server/history.js`) ne fait que lire ces fichiers, exposés via trois routes REST (`GET /api/projects`, `GET /api/sessions?cwd=`, `GET /api/sessions/:sessionId?cwd=`) — pas de WebSocket pour ces données statiques. Dédoublonnage des sessions continuées/forkées par sous-ensemble d'ID de messages (même algorithme que `claude-code-webui`). Le titre réel (`ai-title`/`custom-title`) est récupéré avec un délai après la fin d'un tour (écriture asynchrone sur disque, non confirmée dans quel délai précisément), et immédiatement en cas de reprise d'une session existante. Changer de répertoire de travail réinitialise la conversation (nouvelle session, `allowedTools` vidé) et recharge la liste des sessions de ce répertoire.

**Protocole de permissions (confirmé par lecture de `claude-code-webui`, cloné en local) :** pas de pause/reprise en direct dans un même run. Un outil non autorisé revient simplement comme un `tool_result` avec `is_error: true` (forme confirmée par capture réelle) ; le client détecte ça, coupe la requête en cours (`abort`), affiche le choix fermé (autoriser une fois / toujours / refuser), et en cas d'autorisation, envoie une **nouvelle** requête `--resume <sessionId>` avec l'outil ajouté à `--allowed-tools`. « Autoriser une fois » n'ajoute l'outil que pour cette reprise ; « toujours autoriser » le persiste pour le reste de la session. Implique un suivi minimal de `session_id` côté front, indépendant de la gestion de session complète prévue à l'étape 3. **Non revérifié sous Auto Mode** (voir note `AskUserQuestion` ci-dessous) — à revalider quand `claude -p` sera vraiment branché en remplacement du mock.

**Ligne « Progression » et pop-up de permission enrichi (fait, 2026-10-05).** Une région « Progression » (une seule ligne de texte) est placée sous le formulaire de prompt : « Attente d'un prompt » au repos, sinon l'étape courante du CLI déduite du flux (`system`/`init`, blocs `tool_use`, `thinking`, `text`, `tool_result`) — format « NomOutil texte », nom d'outil jamais traduit, texte coupé à 80 caractères. Case à cocher dans les options (`progressAnnounce`, activée par défaut) : coche = `aria-live="polite"` sur la région, sinon la ligne reste seulement consultable. Après l'envoi d'un prompt, le focus va sur la ligne (au lieu de la zone « Prompt »), avec écriture silencieuse du texte pour éviter une double annonce ; l'ancien « En cours… » de `statusArea` est supprimé à l'envoi (redondant). Un descripteur unique `describeTool(name, input)` (`front/index.js`) renvoie `{ tool, text, external }` et alimente la progression et le pop-up : chemin relatif dans l'espace de travail, chemin complet avec volume sinon (`external` = commence par une lettre de volume ou un séparateur). Pop-up : « Claude veut utiliser l'outil X », texte de l'outil, avertissement si fichier externe, puis ligne « Erreur : … » avec le texte brut du CLI. Non encore unifié : `classifyToolUse` (détail repliable) et sa copie serveur `server/history.js` — à traiter avec l'historique. Non vérifié sur capture réelle : les noms exacts des blocs du flux (`system`/`init`, `thinking`).

**Détection des refus de permission — problème connu et recherches (2026-10-05).**
- *Bug constaté* : `handleIfToolDenied` traite **toute** erreur d'outil (`tool_result.is_error`) comme un refus de permission, coupe le CLI (`abort`) puis affiche le pop-up. Une erreur ordinaire d'`Edit` (« String to replace not found », « File has been modified since read ») provoque donc une boucle : autoriser → relance `--resume` avec « continue » → nouvelle erreur → nouveau pop-up. Constaté sur une session réelle : 157 « continue » et 159 messages `<synthetic>` « No response requested. », **aucun** vrai refus de permission dans le fichier de session.
- *Messages `<synthetic>`* : écrits par le CLI lui-même dans le fichier de session (modèle `<synthetic>`, `stop_reason: stop_sequence`, 0 jeton) quand une relance « continue » n'a rien à reprendre. Normal côté CLI ; c'est la boucle de ClaudeAccess qui les multiplie. À masquer à l'affichage ; ils restent dans le fichier sur disque.
- *Texte réel d'un refus* (issue anthropics/claude-code 54850) : « Claude requested permissions to **write to** \<chemin\>, but you haven't granted it yet. » — le mock disait « to **use** X » : formulation différente. Seule partie commune sûre : « **you haven't granted it yet** ». Pas de texte réel trouvé pour `Edit`, `Bash`, MCP, règles `deny`, hooks, classifieur Auto, ni mode `dontAsk`.
- *Marqueur structuré* : le message final `result` contient `permission_denials` (entrées `tool_name`, `tool_use_id`, `tool_input`) ; sans cela le run finit en `exit 0`, `subtype: "success"`, `is_error: false`. Indépendant de la formulation, couvre aussi `dontAsk`, mais n'arrive qu'à la fin du run.
- *Cas où autoriser est inutile* : en 2.1.123, l'écriture dans `.claude/skills|agents|commands` est refusée même en `bypassPermissions` → boucle assurée sans garde-fou.
- *Correctif prévu* : (1) pop-up seulement si l'erreur contient « you haven't granted it yet » ; (2) confirmation/repli par `permission_denials` à la fin du run ; (3) autres erreurs d'outil : journalisées en console (outil, texte, décision), sans couper le CLI ; (4) jamais de pop-up pour un outil déjà dans `allowedTools` ; (5) garde-fou anti-boucle (même demande deux fois de suite, ou `<synthetic>` « No response requested. » juste après une relance → afficher l'erreur) ; (6) masquer les messages `<synthetic>` dans le journal. Point d'étape avant correctif : le commit « Progress line, permission mode descriptions, richer tool permission popup (WIP) ». Coût de l'approche B (attendre la fin du run), compromis retenu pour l'intérim et approche C (protocole `--permission-prompt-tool stdio`) : voir `open-questions.md`.

**Essais avec le vrai CLI et corrections qui en découlent (2026-10-06).** Neuf exécutions réelles (`haiku`, effort `low`, dossier temporaire, environ 0,15 $), flux bruts relus hors ligne. Constats : (1) à chaque refus le CLI émet `{ type: "system", subtype: "permission_denied", tool_name, tool_use_id, message }` juste avant le `tool_result` d'erreur, et le résultat final liste le refus dans `permission_denials` ; les textes diffèrent selon l'outil et le mode (`Write` et `Edit` : « Claude requested permissions to write to … but you haven't granted it yet. » ; `Bash` : « mkdir in '…' needs approval… » ; `dontAsk` : « Permission to use Write has been denied because Claude Code is running in don't ask mode… ») ; (2) le CLI ne s'arrête pas au refus (1 à 2 tours de plus, résultat `success`) ; (3) `--resume` avec `--allowed-tools` et « continue » garde le même identifiant de session, mais le modèle n'a retenté l'outil qu'une fois sur deux (une fois il a affirmé avoir créé le fichier sans appeler l'outil) : fiabilité de « continue » à tester contre une relance explicite ; (4) `--permission-mode manual` est un alias de `default` ; (5) flux réel : `system/init`, `system/thinking_tokens`, un message assistant par bloc (`thinking` vide, `tool_use`, `text`), `user`/`tool_result`, `rate_limit_event`, `result`. Changements faits : détection des refus par le marqueur `permission_denied` (les motifs de texte sont supprimés, ce qui corrige `dontAsk`), `permission_denials` en repli, tout message du CLI coupé ignoré tant qu'une question est ouverte ; simulateur mis à jour (marqueur, `permission_denials`, réflexion) ; ligne de progression : « Claude réfléchit » déclenché en direct par `thinking_tokens`, une ligne identique n'est pas réécrite ; zone de progression en `<div>` simple sans rôle ni nom (essai jugé « bien plus agréable » : plus de « entrée / sortie de région », justifié dans `spec-interface.md` avec la remarque sur `role="status"`).

**Journal en direct, messages synthétiques et serveur (2026-10-06).** Défaut trouvé : en direct seul le texte du message final (`result`) s'affichait, donc un tour terminé sur un appel d'outil montrait une réponse sans texte et les textes intermédiaires n'apparaissaient qu'après F5 (l'historique, lui, vient du fichier de session). Désormais chaque texte du modèle est ajouté dès l'arrivée de son message, le `result` ne s'ajoute que s'il diffère du dernier texte affiché et un résultat vide n'ajoute rien. Masquage des messages `<synthetic>` affiné : seuls les textes exactement « No response requested. » (tout modèle) et les « continue » seuls sont masqués ; les autres messages synthétiques, comme « You've hit your session limit · resets … », sont affichés sans nom de modèle ni effort (les masquer tous cachait la réponse à un message quand la limite d'usage était atteinte, même après rechargement). Serveur : un prompt envoyé juste après un résultat est accepté (le processus précédent, qui finit encore, est attendu puis arrêté au bout de 2 s) ; une requête REST invalide reçoit un 400 en JSON sans trace en console. Boutons « Dupliquer » et « Déplacer » des sessions retirés (routes et fonctions comprises) : ils manipulaient des fichiers que le CLI possède, la copie était cachée par le dédoublonnage et le déplacement reposait sur une hypothèse non vérifiée sur `--resume`.

**Détection des refus : compromis implémenté (2026-10-05).** Un refus n'ouvre le pop-up (et ne coupe le CLI) que si l'erreur contient « you haven't granted it yet » ; les autres erreurs d'outil sont laissées au modèle ; `permission_denials` du message final sert de repli pour un texte non reconnu (couvre aussi `dontAsk`) ; aucun pop-up pour un outil déjà autorisé (pour toujours ou « une fois » sur ce run, vidé à chaque nouveau prompt) ; toute erreur d'outil est journalisée dans la console du serveur pour collecter les vrais textes. Les outils « toujours autorisés » démarrent vides au lancement, quel que soit le mode, et ne sont jamais sauvegardés. Non encore éprouvé contre le vrai CLI. Comportement détaillé : `spec-interface.md` (section 7) et `spec-server.md`.

**Outils « toujours autorisés » et niveau de permission (2026-10-06).** Chaque mode a un état connu par outil principal (Read, Write, Edit, Bash : demande / autorisé / refusé / vérifié), table `MODE_TOOL_STATES` dans `front/runOptions.js`. La liste envoyée au CLI (`--allowed-tools`) est vidée à chaque changement de mode et à l'ouverture d'une session ou d'un espace ; elle n'est jamais sauvegardée. Quand l'utilisateur autorise « pour toujours » un outil que le mode n'autorise pas, une ligne sous la description du mode l'indique (« Toujours autorisés malgré le mode : Write (le mode demande)… ») ; elle disparaît s'il n'y a pas d'écart. Les états du mode ne sont volontairement pas envoyés au CLI : un `--allowed-tools Write` brut approuverait aussi les écritures hors de l'espace de travail, ce que « Accepter les modifications » ne fait pas.

**Spécifications séparées (2026-10-05).** `doc/spec-server.md` décrit ce que fait le serveur (état persistant, routes REST, canal WebSocket, lecture de l'historique, journal des erreurs d'outil) et `doc/spec-interface.md` ce que fait l'interface (mise en page, espaces de travail, sessions, messages, progression, permissions, options). `plan.md` garde l'historique des décisions, `open-questions.md` les points non tranchés.

**Liste d'espaces de travail côté serveur (fait, 2026-10-05) — revient sur « aucun stockage propre n'est nécessaire ».** Constat : la liste venait de deux sources, `~/.claude.json` (clé `projects`, qui ne contenait qu'une entrée sans dossier d'historique alors que 4 historiques existaient dans `~/.claude/projects`) et le `localStorage` du navigateur (espaces ajoutés, cachés, noms, dernier espace/session), donc liée à un navigateur et à un port : un autre navigateur ou `localhost:1081` repartait de zéro. Désormais : liste propre à l'utilisateur dans `<dossier de config>/workspaces.json` (`~/.claude-access/` ; `server/workspaces.js`, routes `GET`/`PUT /api/workspaces`, remplacement du fichier entier), forme `{ workspaces: [{ path, name?, lastSessionId? }], lastWorkspace }`. Rien n'y entre automatiquement ; `~/.claude.json` n'alimente plus la liste. « Retirer de la liste » supprime l'entrée sans toucher à l'historique ; « Supprimer » efface en plus l'historique ; « Espaces de travail existants… » liste les dossiers d'historique absents de la liste (chemin réel lu dans le champ `cwd` des fichiers de session, le nom de dossier ne se décode pas) pour en ajouter un. Migration unique côté navigateur quand le serveur n'a pas encore de liste (reprend exactement ce que ce navigateur affichait : dossiers connus + ajoutés − cachés, noms, dernier espace/session) ; les anciennes clés `localStorage` sont laissées en place. Comparaison de chemins insensible à la casse, au sens des barres et à la barre finale. Choisir un espace ouvre sa session la plus récente ; la page de messages est positionnée sur la dernière (le champ « page » reçoit son `max` avant sa valeur).

**Options d'exécution relues dans le fichier de session (fait, 2026-10-05).** Le fichier de session de Claude enregistre déjà, par entrée, le modèle (identifiant complet, converti en alias `sonnet`/`haiku`/… côté navigateur), l'effort et le `permissionMode`. À l'ouverture d'une session, `readSessionFile` renvoie les dernières valeurs (`runOptions`, modèle `<synthetic>` ignoré) et elles priment sur la mémoire du navigateur, qui ne sert plus que de repli : n'importe quel navigateur rouvre une session avec ses vraies options (vérifié par l'utilisateur sur un second navigateur : modèle et effort corrects). Les outils « toujours autorisés » restent en mémoire de la page, jamais sauvegardés.

**Messages `<synthetic>` et `continue` masqués (fait, 2026-10-05).** À l'affichage de l'historique rechargé, `server/history.js` ignore les réponses du modèle `<synthetic>`, les réponses réduites à « No response requested. » (quel que soit le modèle) et les messages utilisateur réduits à « continue » ; le journal en direct n'ajoute ni message ni son pour un tour dont la réponse est synthétique. Les fichiers sur disque ne sont pas modifiés. Une vraie réponse qui suit un « continue » est conservée.

**Deux instances (2026-10-05).** `ClaudeDev` est une copie de dossier sans git (nom, port 1081, dossier de config `~/.claude-dev`, lanceur `start-claudedev.bat`) pour faire travailler l'une sur l'autre ; points ouverts dans `open-questions.md`. `plan.md` et `open-questions.md` vivent dans `doc/`.

**`AskUserQuestion` : abandonné (2026-08-20).** Testé directement en lançant un vrai `claude -p` (prompt demandant explicitement d'appeler cet outil, dans un répertoire scratch, sans risque pour le dépôt) avec `--output-format stream-json --verbose`, en nettoyant les variables d'environnement `CLAUDE_*` héritées pour simuler un lancement à froid. Résultat, reproduit avec deux binaires distincts (celui bundlé avec Claude Desktop *et* `@anthropic-ai/claude-code` installé via npm) : le compte utilisé sur cette machine a **Auto Mode** actif par défaut (`claude auto-mode config`), ce qui remplace tout le jeu d'outils standard par un jeu orienté agent autonome/arrière-plan (`Task*`, `Cron*`, `DesignSync`, `PushNotification`, `RemoteTrigger`, `ScheduleWakeup`, `SendMessage`, `Monitor`, `ToolSearch`...). `AskUserQuestion` (comme `TodoWrite`/`ExitPlanMode`) est absent de ce jeu d'outils, y compris des outils différés (confirmé par énumération complète via `ToolSearch`) — il ne peut donc structurellement pas être invoqué en l'état. Tentative de désactiver Auto Mode pour le test via `--settings` : bloquée par le classificateur Auto Mode lui-même (« Auto-Mode Bypass ») — pas de contournement cherché plus loin. Désactiver Auto Mode se ferait via `/auto-mode-setup` ou `~/.claude/settings.json`, mais c'est un réglage par compte/machine (pas par projet) : décision prise de ne pas y toucher, par simplicité. Conséquence : le protocole `AskUserQuestion` (`user_question`/`user_question_response`) a été retiré du mock, du serveur et du front — plus aucune trace dans le code, seule cette note en garde l'historique. Le protocole de permissions ci-dessus reste, lui, en place (implémenté indépendamment).

## Points de vigilance

- **Risque `--bare`** : la doc officielle indique que `--bare` (qui n'accepte que `ANTHROPIC_API_KEY`, pas l'abonnement Pro/Max OAuth) deviendra le comportement par défaut de `-p` dans une future version. Plusieurs issues GitHub confirment que ce n'est aujourd'hui pas résolu pour les utilisateurs OAuth. On reste volontairement sur l'invocation directe de `claude -p` (sans `--bare`) tant que ce n'est pas le défaut ; à surveiller au fil des mises à jour de `claude`.
- **SDK vs CLI direct** : décision de rester sur l'invocation directe du binaire `claude` plutôt que le SDK `@anthropic-ai/claude-code`. Le SDK ne fait que spawn le même binaire (vu dans le code de `claude-code-webui`) : ça ne réduit pas le risque `--bare` ci-dessus. Vérifié aussi que l'usage personnel auto-hébergé (comme ce projet) reste dans le cadre toléré par la politique d'utilisation d'Anthropic (clarification de février 2026 sur l'OAuth des abonnements dans des outils tiers) : la restriction vise les services multi-tenant, pas un outil personnel utilisant son propre abonnement.
